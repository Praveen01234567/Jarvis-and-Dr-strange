CHAPTER 01

Anatomy of a PL/SQL Block

Every PL/SQL program — anonymous block, procedure, or function — follows the same four-part skeleton. Memorize this shape first; everything else (cursors, exceptions, bulk operations) just fills in these sections.

anonymous_block.sql
DECLARE
   -- variables, cursors, types declared here (optional section)
   v_emp_name  VARCHAR2(50);
BEGIN
   -- executable statements go here (mandatory)
   SELECT ename INTO v_emp_name FROM emp WHERE empno = 7369;
   DBMS_OUTPUT.PUT_LINE('Hello, ' || v_emp_name);
EXCEPTION
   WHEN NO_DATA_FOUND THEN
      DBMS_OUTPUT.PUT_LINE('No such employee.');
END;
/
Interview one-liner: "DECLARE is optional, BEGIN...END is mandatory, EXCEPTION is optional but recommended." Say this and the interviewer knows you understand the structure, not just memorized code.
CHAPTER 02

Implicit Cursors — Oracle's Silent Worker

Every single INSERT, UPDATE, DELETE or single-row SELECT INTO automatically gets a cursor created behind the scenes — Oracle calls it SQL%. You never OPEN/FETCH/CLOSE it; you just read its attributes right after the statement.

implicit_cursor.sql
BEGIN
   UPDATE emp SET sal = sal * 1.1 WHERE deptno = 10;

   IF SQL%FOUND THEN
      DBMS_OUTPUT.PUT_LINE(SQL%ROWCOUNT || ' rows got a raise.');
   ELSE
      DBMS_OUTPUT.PUT_LINE('No rows matched.');
   END IF;
END;
/
AttributeMeaning
SQL%FOUNDTRUE if the statement affected ≥1 row
SQL%NOTFOUNDTRUE if it affected 0 rows
SQL%ROWCOUNTNumber of rows affected
SQL%ISOPENAlways FALSE for implicit cursors (closed instantly)
Common trap question: "Is SQL%ISOPEN ever TRUE?" → No, for implicit cursors Oracle opens and closes it instantly, so it's always FALSE when you check it.
CHAPTER 03

Explicit Cursors — OPEN · FETCH · CLOSE

When a query returns multiple rows and you need to process them one at a time, you declare your own cursor and drive it manually through three steps: OPEN it, FETCH one row at a time into variables, then CLOSE it. A loop that checks %NOTFOUND stops the fetching.

explicit_cursor.sql
DECLARE
   CURSOR c_emp IS
      SELECT empno, ename, sal FROM emp WHERE deptno = 10;
   v_empno  emp.empno%TYPE;
   v_ename  emp.ename%TYPE;
   v_sal    emp.sal%TYPE;
BEGIN
   OPEN c_emp;
   LOOP
      FETCH c_emp INTO v_empno, v_ename, v_sal;
      EXIT WHEN c_emp%NOTFOUND;
      DBMS_OUTPUT.PUT_LINE(v_ename || ' earns ' || v_sal);
   END LOOP;
   CLOSE c_emp;
END;
/

CHAPTER 04

Cursor FOR Loop — the shortcut

90% of explicit-cursor code in the real world is replaced by a cursor FOR loop. Oracle implicitly OPENs, FETCHes every row, and CLOSEs the cursor for you — no variables to declare, no NOTFOUND check.

cursor_for_loop.sql
BEGIN
   FOR r_emp IN (SELECT empno, ename, sal FROM emp WHERE deptno = 20)
   LOOP
      DBMS_OUTPUT.PUT_LINE(r_emp.ename || ' -> ' || r_emp.sal);
   END LOOP;
END;
/

CHAPTER 05

Parameterized Cursors

A cursor can accept parameters just like a procedure — letting you reuse one cursor definition for many filter values instead of writing a new cursor every time.

param_cursor.sql
DECLARE
   CURSOR c_emp(p_dept NUMBER, p_min_sal NUMBER) IS
      SELECT ename, sal FROM emp
      WHERE deptno = p_dept AND sal >= p_min_sal;
BEGIN
   FOR r IN c_emp(10, 2000) LOOP
      DBMS_OUTPUT.PUT_LINE(r.ename || ' : ' || r.sal);
   END LOOP;
END;
/

CHAPTER 06

REF CURSOR — cursors you can pass around

A normal cursor's query is fixed at compile time. A REF CURSOR is a pointer to a result set, so you can open it with different queries at runtime and pass it out of a procedure — typically back to a calling Java/.NET app or another PL/SQL block.

ref_cursor.sql
DECLARE
   TYPE t_ref_cursor IS REF CURSOR;   -- weak ref cursor
   v_cur     t_ref_cursor;
   v_ename   emp.ename%TYPE;
   v_sal     emp.sal%TYPE;
   v_choice  VARCHAR2(10) := 'HIGH';
BEGIN
   IF v_choice = 'HIGH' THEN
      OPEN v_cur FOR SELECT ename, sal FROM emp WHERE sal > 3000;
   ELSE
      OPEN v_cur FOR SELECT ename, sal FROM emp WHERE sal <= 3000;
   END IF;

   LOOP
      FETCH v_cur INTO v_ename, v_sal;
      EXIT WHEN v_cur%NOTFOUND;
      DBMS_OUTPUT.PUT_LINE(v_ename || ' - ' || v_sal);
   END LOOP;
   CLOSE v_cur;
END;
/

-- SYS_REFCURSOR is Oracle's built-in weak REF CURSOR type, used 95% of the time:
PROCEDURE get_emps(p_dept NUMBER, p_cur OUT SYS_REFCURSOR) IS
BEGIN
   OPEN p_cur FOR SELECT * FROM emp WHERE deptno = p_dept;
END;
TypeWhat it isWhen to use
Strong REF CURSORHas a fixed RETURN type, e.g. RETURN emp%ROWTYPEYou want compile-time column checking
Weak REF CURSORNo RETURN type — works with any queryGeneric, reusable code (most common)
SYS_REFCURSOROracle's pre-defined weak ref cursor typeDefault choice — no need to declare your own TYPE

CHAPTER 07

BULK COLLECT — fetch many rows in one trip

Fetching row-by-row means one context switch between the PL/SQL engine and the SQL engine per row — slow for large data. BULK COLLECT INTO fetches the whole result set (or a chunk of it, with LIMIT) into a collection in a single context switch.

bulk_collect.sql
DECLARE
   TYPE t_sal_tab IS TABLE OF emp.sal%TYPE;
   v_sals  t_sal_tab;
BEGIN
   SELECT sal BULK COLLECT INTO v_sals FROM emp;   -- one round trip
   DBMS_OUTPUT.PUT_LINE('Fetched ' || v_sals.COUNT || ' salaries');

   -- with a cursor + LIMIT, to avoid loading millions of rows into memory at once:
   DECLARE
      CURSOR c_emp IS SELECT sal FROM emp;
      TYPE t_tab IS TABLE OF emp.sal%TYPE;
      v_chunk t_tab;
   BEGIN
      OPEN c_emp;
      LOOP
         FETCH c_emp BULK COLLECT INTO v_chunk LIMIT 100;
         EXIT WHEN v_chunk.COUNT = 0;
         -- process v_chunk(1..v_chunk.COUNT) here
      END LOOP;
      CLOSE c_emp;
   END;
END;
/

CHAPTER 08

FORALL — bulk DML, the write-side twin of BULK COLLECT

If BULK COLLECT is bulk reading, FORALL is bulk writing. Instead of looping and issuing one UPDATE/INSERT/DELETE per row (N round trips), FORALL sends the whole batch of values to the SQL engine in one round trip.

forall.sql
DECLARE
   TYPE t_id_tab IS TABLE OF emp.empno%TYPE;
   v_ids   t_id_tab;
BEGIN
   SELECT empno BULK COLLECT INTO v_ids FROM emp;

   FORALL i IN v_ids.FIRST..v_ids.LAST SAVE EXCEPTIONS
      UPDATE emp SET sal = sal * 2 WHERE empno = v_ids(i);

   COMMIT;
EXCEPTION
   WHEN OTHERS THEN
      FOR j IN 1..SQL%BULK_EXCEPTIONS.COUNT LOOP
         DBMS_OUTPUT.PUT_LINE('Row ' || SQL%BULK_EXCEPTIONS(j).ERROR_INDEX ||
            ' failed: ' || SQLERRM(-SQL%BULK_EXCEPTIONS(j).ERROR_CODE));
      END LOOP;
END;
/
Without FORALLWith FORALL
N UPDATE statements → N context switches1 UPDATE statement, N times internally → 1 context switch
Stops entirely on first error (unless handled)SAVE EXCEPTIONS lets all rows attempt, then reports every failure via SQL%BULK_EXCEPTIONS
Classic trap: FORALL can only contain one single DML statement — you cannot put two UPDATEs or an IF inside a FORALL body. If you need conditional logic, filter the collection beforehand.
CHAPTER 09 · CAPSTONE

The Classic Interview Task: Double Everyone's Salary

This is the exercise that combines everything above. Watch how the same business outcome — doubling sal — is written three ways, from slowest to fastest, and run all three against your table to compare.

v1_row_by_row.sql — slow
BEGIN
   FOR r IN (SELECT empno FROM emp) LOOP
      UPDATE emp SET sal = sal * 2 WHERE empno = r.empno;  -- 1 round trip PER row
   END LOOP;
   COMMIT;
END;
/
v2_single_set_update.sql — best for a plain "double everyone" task
BEGIN
   UPDATE emp SET sal = sal * 2;   -- 1 statement, 1 round trip, set-based
   COMMIT;
END;
/
v3_bulk_collect_forall.sql — what they actually want to hear in interviews
DECLARE
   TYPE t_id_tab  IS TABLE OF emp.empno%TYPE;
   CURSOR c_emp IS SELECT empno FROM emp;
   v_ids  t_id_tab;
BEGIN
   OPEN c_emp;
   LOOP
      FETCH c_emp BULK COLLECT INTO v_ids LIMIT 500;  -- read in chunks
      EXIT WHEN v_ids.COUNT = 0;

      FORALL i IN v_ids.FIRST..v_ids.LAST SAVE EXCEPTIONS
         UPDATE emp SET sal = sal * 2 WHERE empno = v_ids(i);  -- write in one shot
   END LOOP;
   CLOSE c_emp;
   COMMIT;
END;
/
Why version 3 still matters even though version 2 is shorter: interviewers use "double the salary" as a proxy question to see if you know BULK COLLECT + FORALL — for a real plain doubling task, the single UPDATE (v2) is genuinely the right answer; v3's pattern is what you'd use when each row needs row-specific logic that a plain SET can't express (e.g. different multipliers per grade, calling a function per row, or writing to a log table per row).

CHAPTER 10

UTL_FILE — reading and writing OS files

UTL_FILE lets PL/SQL read from and write to text files on the database server's filesystem (inside a directory registered as an Oracle DIRECTORY object). Common use: exporting a report, or loading a flat file's data into a table.

utl_file_write.sql
-- one-time DBA setup:
CREATE OR REPLACE DIRECTORY emp_dir AS '/u01/app/exports';
GRANT READ, WRITE ON DIRECTORY emp_dir TO hr;

DECLARE
   v_file  UTL_FILE.FILE_TYPE;
BEGIN
   v_file := UTL_FILE.FOPEN('EMP_DIR', 'emp_export.csv', 'W');

   FOR r IN (SELECT empno, ename, sal FROM emp) LOOP
      UTL_FILE.PUT_LINE(v_file, r.empno || ',' || r.ename || ',' || r.sal);
   END LOOP;

   UTL_FILE.FCLOSE(v_file);
EXCEPTION
   WHEN UTL_FILE.INVALID_PATH THEN
      DBMS_OUTPUT.PUT_LINE('Directory object not found or no access.');
END;
/
utl_file_read.sql
DECLARE
   v_file  UTL_FILE.FILE_TYPE;
   v_line  VARCHAR2(4000);
BEGIN
   v_file := UTL_FILE.FOPEN('EMP_DIR', 'emp_export.csv', 'R');
   LOOP
      BEGIN
         UTL_FILE.GET_LINE(v_file, v_line);
         DBMS_OUTPUT.PUT_LINE(v_line);
      EXCEPTION
         WHEN NO_DATA_FOUND THEN EXIT;
      END;
   END LOOP;
   UTL_FILE.FCLOSE(v_file);
END;
/

CHAPTER 11

Global Temporary Tables (GTT)

A GTT has a permanent structure but session-private or transaction-private data — perfect for staging intermediate results during a complex batch job without different sessions seeing each other's rows.

gtt.sql
CREATE GLOBAL TEMPORARY TABLE gtt_emp_staging (
   empno  NUMBER,
   sal    NUMBER
) ON COMMIT DELETE ROWS;   -- or ON COMMIT PRESERVE ROWS

BEGIN
   INSERT INTO gtt_emp_staging SELECT empno, sal FROM emp WHERE sal > 3000;
   -- ... do further processing on the staged rows ...
   COMMIT;  -- with DELETE ROWS, gtt_emp_staging is now empty again
END;
/
OptionBehaviour
ON COMMIT DELETE ROWSDefault. Rows are wiped automatically at every COMMIT (transaction-private).
ON COMMIT PRESERVE ROWSRows survive COMMIT, but are wiped when the session ends (session-private).
LIVE LAB · stage rows, then COMMIT and watch ON COMMIT DELETE ROWS clear them
Stage rows, inspect the table, then COMMIT to see it auto-clear.
Interview comparison they love to ask: GTT vs. a normal table used as staging → GTT needs no manual cleanup (no DELETE/TRUNCATE step), generates much less redo/undo, and different sessions never see each other's data even though they share one table definition.
